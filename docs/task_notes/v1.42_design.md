# v1.42 Design

## Status

- Design only.
- No implementation code has been started in this note.

## Unique goal

Build `v1.42` as a manifest-driven benchmark production layer so the repo can stably emit paper main results, significance analysis, prompt provenance, and a submission-ready package from one declared experiment definition.

This milestone is explicitly about result production, not about improving retrieval quality, changing segmentation logic, or rewriting the existing offline/runtime pipeline.

## Why this version should avoid oversized orchestrators

The current highest-risk files are already oversized and own too many contracts:

- `src/pov_compiler/pipeline.py`
- `src/pov_compiler/retrieval/retriever.py`
- `src/pov_compiler/streaming/runner.py`
- `scripts/eval_nlq.py`

Reasons to avoid them in `v1.42`:

1. They sit on top of fragile cross-module contracts.
   `Output`, `events_v1`, repo chunks, strict metrics, and chain/query-aware retrieval all converge there.

2. The existing tests cover them mostly through behavior and smoke paths, not by one narrow refactor-safe API.

3. `v1.42` does not need runtime semantics changes.
   The milestone can be delivered by orchestrating and packaging existing outputs more coherently.

4. Editing them would mix two jobs:
   benchmark productionization and core algorithm/runtime evolution. That would slow implementation and make regressions harder to isolate.

Conclusion:
`v1.42` should be additive. New benchmark/suite/significance/prompt/export logic belongs in new files, not inside the existing runtime cores.

## Design scope

### 1. Experiment Manifest

Purpose:
one declarative file describing what benchmark to run, which outputs to collect, which prompt profile to lock, which significance tests to compute, and which export profile to produce.

Proposed new files:

- `configs/benchmarks/v1.42_main.yaml`
- `src/pov_compiler/bench/manifest.py`
- `tests/test_benchmark_manifest.py`

Manifest responsibilities:

- identify the suite:
  `suite_id`, `suite_version`, `seed`, `description`
- define inputs:
  `uids_file`, `compare_dir`, optional task-specific roots
- define lanes:
  `nlq`, `bye`, `streaming`, `repo`, `planner_backend`, `decisions_backend`, `model_stack`
- define budgets and labels:
  `label_a`, `label_b`, budget points, selected tasks
- define prompt provenance:
  `prompt_registry`, `prompt_profile`, `prompt_lock_required`
- define significance policy:
  primary metrics, alpha, correction method, bootstrap/permutation settings
- define export profile:
  `paper_ready`, `submission_pack`, figure formats, required tables

Boundary:
the manifest describes runs and collection. It does not replace `configs/default.yaml` or low-level runtime configs.

### 2. Benchmark Suite Runner

Purpose:
execute or collect benchmark lanes through stable CLI boundaries and write one normalized suite snapshot.

Proposed new files:

- `scripts/run_benchmark_suite.py`
- `src/pov_compiler/bench/suite_runner.py`
- `tests/test_benchmark_suite_runner_smoke.py`

Runner design:

- consume `configs/benchmarks/v1.42_main.yaml`
- invoke existing scripts via subprocess, not deep imports into oversized orchestrators
- support `run`, `resume`, and `collect-only` modes
- record every command, output root, and exit code
- validate required downstream artifacts before marking a lane successful

Primary output layout:

```text
data/outputs/<suite_run>/
  manifest/
    experiment_manifest.yaml
    manifest_resolved.json
    prompt_lock.json
  suite/
    task_status.csv
    run_log.jsonl
    commands.sh
    suite_report.md
    suite_snapshot.json
  compare/
    ...
  significance/
    ...
  paper_ready/
    ...
```

Key design rule:
the runner should treat current compare/sweep/export scripts as stable producers and avoid re-implementing their internal logic.

### 3. Statistical Significance Pipeline

Purpose:
turn benchmark outputs into publishable statistical support for main claims.

Proposed new files:

- `scripts/run_statistical_significance.py`
- `src/pov_compiler/bench/reporting/significance.py`
- `tests/test_statistical_significance.py`

Input contract:

- suite snapshot and manifest
- per-budget aggregate CSVs already emitted by compare/sweep scripts
- per-uid or per-setting tables where available

Methods to design for:

- paired bootstrap confidence intervals for primary deltas
- paired permutation test or sign test for paired A/B comparisons
- Benjamini-Hochberg FDR correction across declared primary endpoints

Planned outputs:

```text
significance/
  tables/
    table_significance_main.csv
    table_significance_main.md
    table_confidence_intervals.csv
    table_confidence_intervals.md
  figures/
    fig_significance_delta_vs_budget_seconds.png
    fig_significance_delta_vs_budget_seconds.pdf
    fig_effect_size_forest.png
    fig_effect_size_forest.pdf
  report.md
  snapshot.json
```

Non-goal:
`v1.42` significance should not require changes to `scripts/eval_nlq.py`. It should read the artifacts that evaluation already writes.

### 4. Prompt Registry

Purpose:
version prompts as first-class reproducibility artifacts and export exactly which prompt texts/profiles were associated with a benchmark result.

Proposed new files:

- `configs/prompts/registry_v1.yaml`
- `prompts/decisions/model_decision_v1.txt`
- `prompts/planner/model_planner_v1.txt`
- `prompts/repository/repo_summary_v1.txt`
- `src/pov_compiler/prompts/__init__.py`
- `src/pov_compiler/prompts/registry.py`
- `scripts/validate_prompt_registry.py`
- `tests/test_prompt_registry.py`

Registry design:

- each entry has:
  `prompt_id`, `task`, `version`, `path`, `owner`, `tags`, `frozen`, `notes`
- registry supports validation, resolution, hashing, and export to a prompt lock file
- suite runner records the resolved prompt set used by a run into `prompt_lock.json`

Implementation boundary:

- base `v1.42` requirement:
  registry must be file-backed, validatable, snapshot-able, and exportable
- optional escalation:
  only if runtime prompt selection is required for suite reproducibility, allow narrow edits to:
  - `src/pov_compiler/l3_decisions/model_compiler.py`
  - `src/pov_compiler/retrieval/model_planner.py`
  - `src/pov_compiler/repository/summarizer.py`

The default design assumes prompt provenance can be delivered without touching those files in phase one.

### 5. Submission-ready export

Purpose:
extend the existing paper-ready export so it can emit a full `submission_pack/` instead of only copied tables/figures/snapshots.

Primary existing file to modify:

- `scripts/export_paper_ready.py`

Planned additive behavior:

- keep current `tables/`, `figures/`, `report.md`, and `snapshot.json`
- accept suite and significance inputs
- copy prompt registry and prompt lock artifacts
- emit `submission_pack/` under the paper-ready output root

Proposed `submission_pack/` layout:

```text
paper_ready/
  tables/
  figures/
  report.md
  snapshot.json
  submission_pack/
    README.md
    manifest/
      experiment_manifest.yaml
      manifest_resolved.json
      prompt_lock.json
    paper_ready/
      tables/
      figures/
      report.md
      snapshot.json
    significance/
      tables/
      figures/
      report.md
      snapshot.json
    prompts/
      registry_v1.yaml
      decisions/
      planner/
      repository/
    provenance/
      suite_snapshot.json
      commands.sh
      task_status.csv
```

Compatibility rule:
existing `export_paper_ready.py` outputs must stay valid even when `submission_pack/` is not requested.

### 6. xdist test acceleration entry

Purpose:
make fast local validation the default developer path for `v1.42`.

Existing file to reuse:

Design decision:

- do not add another test wrapper
- document `python scripts/test_fast.py` as the official local fast-test entry
- use it in `README.md` and `v1.42` validation instructions

## Test plan

### Unit tests

- `tests/test_benchmark_manifest.py`
  validates manifest schema, defaults, required fields, and resolved paths
- `tests/test_prompt_registry.py`
  validates prompt registry loading, hashing, duplicate detection, and prompt-lock generation
- `tests/test_statistical_significance.py`
  validates bootstrap CI, paired-test output shape, and FDR correction on tiny fixtures

### Smoke/integration tests

- `tests/test_benchmark_suite_runner_smoke.py`
  runs a tiny manifest in `collect-only` or fixture-backed mode and verifies suite outputs
- extend `tests/test_export_paper_ready_smoke.py`
  to verify:
  - significance tables/figures can be copied
  - prompt registry assets are copied
  - `submission_pack/` is created and populated

### Validation commands

```powershell
python -m pytest -q tests/test_benchmark_manifest.py tests/test_prompt_registry.py tests/test_statistical_significance.py tests/test_benchmark_suite_runner_smoke.py tests/test_export_paper_ready_smoke.py
```

## Minimal smoke plan

1. Validate prompt registry only.

```powershell
python scripts/validate_prompt_registry.py --registry configs/prompts/registry_v1.yaml
```

2. Run suite runner in fixture-backed `collect-only` mode from a tiny manifest.

```powershell
python scripts/run_benchmark_suite.py --manifest configs/benchmarks/v1.42_main.yaml --mode collect-only --out_dir data/outputs/v142_smoke
```

3. Run significance over the collected smoke outputs.

```powershell
python scripts/run_statistical_significance.py --suite_dir data/outputs/v142_smoke --out_dir data/outputs/v142_smoke/significance
```

4. Export paper-ready plus submission-pack from the same smoke root.

```powershell
python scripts/export_paper_ready.py --compare_dir data/outputs/v142_smoke/compare --out_dir data/outputs/v142_smoke/paper_ready
```

Smoke success criteria:

- all commands return zero
- suite snapshot exists
- significance tables exist
- paper-ready `tables/`, `figures/`, `snapshot.json`, and `submission_pack/` exist
- prompt lock is present in the submission package

## Output artifact plan

### Tables

- existing paper-ready tables remain:
  `table_budget_panel.*`, `table_budget_panel_delta.*`
- new significance tables:
  `table_significance_main.*`, `table_confidence_intervals.*`
- suite-level tracking:
  `suite/task_status.csv`

### Figures

- existing budget panel figures remain unchanged
- new significance figures:
  `fig_significance_delta_vs_budget_seconds.*`
  `fig_effect_size_forest.*`

### Snapshots

- suite snapshot:
  `suite/suite_snapshot.json`
- significance snapshot:
  `significance/snapshot.json`
- paper-ready snapshot:
  `paper_ready/snapshot.json`

### Paper-ready

`paper_ready/` remains the main human-facing output root and stays backward-compatible with the current exporter contract.

### Submission pack

`paper_ready/submission_pack/` becomes the archival artifact for paper delivery. It must include:

- resolved experiment manifest
- prompt lock and prompt source files
- paper-ready tables/figures/report/snapshot
- significance tables/figures/report/snapshot
- command and status provenance

## Risks and boundaries

Biggest risk:
turning `v1.42` into a runtime refactor instead of a packaging/reproducibility milestone.

Control measures:

- new files first
- only one existing exporter edited by default
- no edits to oversized orchestrators
- prompt registry initially treated as reproducibility infrastructure, not mandatory runtime rewiring

## Recommended implementation order

1. Manifest loader and tiny suite snapshot writer
2. Prompt registry loader and prompt-lock export
3. Significance pipeline over fixture CSVs
4. `export_paper_ready.py` submission-pack extension
5. README update
6. smoke and targeted tests
